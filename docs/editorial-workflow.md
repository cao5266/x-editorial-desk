# X 选题、核验与审稿手册

## 1. 采集只产出线索

- **Freebie Radar**：发现实用工具、社区新项目、免费额度和优惠线索；既有 AI 审核结果仅供初筛。
- **Miniflux**：看项目发布记录、官方博客和维护者文章；跳过例行构建、重复版本和没有实际用途的变更。
- **changedetection.io**：看官方页面、价格与权益条款的实质变化；排除首次快照、相对日期、计数器和排版噪声。

每轮先运行[三源只读采集](server-operations.md#从工作站生成三路选题批次)，默认近 24 小时，48 小时补漏。记录窗口、批次路径、三个服务的状态、返回数量、异常和过滤原因。`partial` 的现有结果可用，但不得写成全量；`failed` 是读不到或没有可靠覆盖，不能记成没有新增。只有成功、覆盖正常且记录数为 0，才记为 `empty`。三路都查，不要求同一选题三路都命中。

### 批次怎样交给编辑

1. Miniflux 看入库时间 `created_at`；Radar 看 `first_seen_at`。另列来源提供的发布时间，未知就留空，到一手来源核对。changedetection 看快照时间，先在历史页比对前一版，首次快照不算变更；计数器、顺序、导航、相对日期变化不算选题。抓取状态只说明采集，不证明事实或发布时间。
2. 批次先将同一规范化文章 URL 分组，保留各源记录 ID。再人工把不同 URL 指向的同一事件合并：用「规范项目／权益 + 发生的事 + 版本或生效日」作为事件键，同时核对一手链接。仓库主页和具体 release 不自动合并，同一版本不同转载可并，同一 changelog 不同更新不能并。旧窗口的同一事件也检查已有审稿包和发布记录，保留沿用或重开的理由。
3. 每个候选留「入选／待补证／淘汰／常青」和一条理由。超过窗口的好材料走常青，不写成刚发布。没有候选通过就记「本轮不发」，不用拿例行构建或媒体快讯填空。

## 2. 选题卡必须能落到行动

先写一张卡：**栏目｜谁会用｜具体任务｜为什么值一条｜第一步｜必要限制／成本**。候选必须能说明一个真实场景、可操作的入口和不用猜的前置条件。例行 Build、内部依赖更新或只改版式，除非能讲清给目标读者带来什么变化，否则淘汰。免费权益有地域、资格、额度、时效或扣费关键项不能确认，标「待补证」；别用「免费」代替条件。

| 栏目 | 核验重点 | 推荐配图 |
| --- | --- | --- |
| 实用工具 | 官方功能、使用入口、计划／平台限制；能否用一个无敏感数据的样例演示。 | 脱敏界面截屏、输入→输出示意；没有实测就不用结果对比图。 |
| 开源／工作流 | 原仓库、相关版本、许可证（若声称开源）、运行环境、依赖、是否要密钥或付费。不要把「可看源码」等同于开源。 | 最短流程图、终端或结果截图；说明版本和条件。 |
| 免费权益 | 官方领取入口、身份及地区资格、额度和周期、领取期限或用完即止、绑卡、到期／超额／自动续费规则。不能确认免扣费时，不写「零成本」。 | 「谁能领／能领多少／何时到期」条件卡，或带核验日期的官方条款截图。 |

安全事件不是独立栏目。即使原文可核验，也要能转成与账号定位相符的、可照着做的工具或工作流指南，才值得继续；否则不主推。

## 3. 先核验，后写稿；证据和图文一起审

先打开官方公告、版本说明、使用文档、原仓库或原作者记录。确认发布时间、可用功能、复现入口和限制，不按采集摘要扩写。记录每个关键说法的证据链接、段落或短摘录、核验时间、产品版本和结论。只保存可分享的证据摘录；用得上的失败记录只留分类和时间。

- **已实测**：保留环境、版本、日期、输入与实际结果。测试成功只覆盖该场景，不外推所有网页、账号或方案。
- **官方说明，未实测**：可写文档明确支持的能力和官方步骤，正文写「官方说明，未实测」；用「可以先用……试」而非「我用它成功……」。同一家公司发布的公告和文档不算两份独立实测。
- **待核验**：打不开一手来源、功能边界不清楚，或无法确认权益是否仍有效。暂存；除非删除相关说法仍能给读者明确价值，否则不交待发布定稿。

开头给用途或要解决的麻烦。正文用一个具体动作解释怎样开始，用必要条件给读者判断，不用固定顺序。单个用法优先短帖；只有多个前置条件、不可省的配置或取舍需要展开才做串帖，每条都要推进读者一步。按 [X 的加权长度规则](https://docs.x.com/fundamentals/counting-characters)检查可复制正文，发布前由人工在编辑器再看一遍。删掉营销套话、复述标题和没根据的「更快／更省」。

每稿单独建目录：`README.md` 记事件键、三路来源与批次、决策理由、逐项证据、核验时间、版本和审核记录；`x-post.txt` 放可复制正文；`image-brief.md` 放图上的字、图型、替代文字和证据，成图如有放同目录。配图必须解释步骤、条件或结果，没增量就不配。示意图显著标「示意 / 未实测」，禁用仿官方 UI、假截图或未验证效果；使用真实截图先脱敏。改正文、图或证据后升版，回到待人工审核。

## 4. 用现有候选做尺度校准

- **OpenRouter 数据事件**：保留为资料，不作为这批主推。若以后有适合读者的切口，可另做「如何核对模型请求走哪家供应商」的工作流；把官方步骤和实测结果分开，不把事件重新包装成新闻。
- **Lindy 浏览器操作**：保留为工具候选。优先讲一个具体任务，例如用测试表单演示「打开页面 → 填写样例 → 检查结果」。尚未跑过时写「官方说明，未实测」；MCP 管理任务和网页操作是两个能力，不能合写成「从 MCP 操作任意网页」。

## 5. 审核与发布是两次决定

| 状态 | 进入条件 | 需要留下什么 |
| --- | --- | --- |
| 初稿（可标待人工审核） | 可把图文证据交人检查，未获批准 | 版本、文件名、各说法及配图证据、待审核项 |
| 已审核 | 人工对指定版本确认文案和图，允许作为成品 | 审核人、时间、审过的版本；不等于授权发布 |
| 待发布 | 有明确的发布授权、账号和可用渠道；或已尝试但仍待确认 | 发布人、渠道、授权时间、确认状态；确认不明不重发 |
| 已发布 | 拿到并核对打开可见的真实帖子链接：账号、内容、配图与串帖顺序符合指定版本 | 真实帖子链接、核对人、时间；串帖同时核对各条是否齐全 |

台账可记录在各稿审阅包里：`时间｜版本｜前状态 → 后状态｜人工操作人｜依据／帖子链接`。用户报告 Grok Bot 的带图发布确认有局限；仓库没有该 Bot 的实现或真实运行凭据，本轮也未联调。上传成功、媒体 ID、排队成功、Bot 口头说成功都不足以证明帖子发出。遇到确认缺失，保持「待发布 / 发布结果未确认」，交人工到 X 核对；不得绕过确认、自动重试或用图片 URL 当帖子链接。没有发布授权，不调用 Bot、X 或编辑器。
